## 1. Unified search across independently built sub-sites

**Pagefind multisite / `mergeIndex`**
- For: Purpose-built for exactly this shape. `pagefind.mergeIndex(bundlePath, opts)` (JS API) or `mergeIndex: [{bundlePath, ...}]` (Component UI) merges N independently-built Pagefind bundles into one query at *browser* runtime — no server-side merge step. Works because Pagefind indexes are static files (WASM + chunked index) generated by a post-build CLI step that reads plain generated HTML — it does not care whether the HTML came from VitePress, Astro, mdBook, or MkDocs Material; "all static site generators are supported, as long as the built HTML contains the content." [Pagefind docs](https://pagefind.app/docs/multisite/), [Pagefind repo](https://github.com/Pagefind/pagefind)
- Same-origin: no config needed if all bundles are same-origin (path-mounted under one domain is exactly this case — `/docs/pagefind/`, `/catalog/pagefind/`, etc.). Cross-origin bundles need CORS headers on the bundle folder.
- Ranking: `indexWeight` lets you bias relative importance per sub-index; language mismatch falls back to the *main* index's WASM/language, so all merged indexes are searched using the primary instance's module — mixed-language sub-sites need explicit `language` overrides.
- Size/perf: index is chunked, only relevant chunks fetched per query; ~300kB total payload observed on a 10k-page site, most sites closer to 100kB. 2026 releases moved search execution into a Web Worker and shrank chunks ~45% via delta-encoding. [pagefind.app](https://pagefind.app/), [GH issues #1119](https://github.com/Pagefind/pagefind/issues/1119)
- Against: `mergeIndex` combines indexes **client-side at query time**, each as a separate query against a separate bundle — the maintainer explicitly said combining pre-built indexes into one physical index is unsupported and "in the too hard basket" (no plans). For >10 sub-sites this is "vaguely efficient" per maintainer — you pay per-site query cost even though asset loading is shared. [GH discussion #564](https://github.com/CloudCannon/pagefind/discussions/564)
- Workaround mentioned by maintainer for large fan-out: mount all built HTML into one folder tree and run a single `pagefind --site` indexing pass over the aggregate, rather than merging separately-built indexes. This trades independent-repo-build convenience for one unified index but avoids the N-query cost.

**Alternatives**
- Algolia DocSearch (crawler): free for OSS/technical docs; crawler is Algolia's proprietary hosted service (the open-source `docsearch-scraper` was deprecated in 2021). Crawls by URL/sitemap across arbitrary paths — path-mounted multi-generator site is a non-issue since it's just crawling rendered HTML. Config via `exclusionPatterns`/`stop_urls` for path control. [docsearch.algolia.com](https://docsearch.algolia.com/docs/crawler/), [GitHub algolia/docsearch](https://github.com/algolia/docsearch)
  - Against: requires manual application/approval to Algolia's OSS program, external dependency on Algolia's index + hosted search widget (not fully self-hosted/static), less control than a build-time static index.
- Typesense `docsearch-scraper` fork: same crawler logic as legacy Algolia scraper but indexes into a self-hosted Typesense cluster. Fully OSS, no vendor lock, but you now operate a Typesense server (not purely static/CDN-only). [typesense/typesense-docsearch-scraper](https://github.com/typesense/typesense-docsearch-scraper)
- Orama: has a free cloud tier, in-browser/edge-native queries, good for small doc sets; less proven at scale than Typesense/Algolia per 2026 comparisons.
- Meilisearch: Community Edition is single-node (no built-in replication/HA without Cloud/Enterprise); LMDB storage; good multi-language support.
- negative: none of Typesense/Meilisearch/Orama are "static-only" — all require running or paying for a search server, unlike Pagefind which needs zero infrastructure. For a free OSS project on Bunny CDN (pure static hosting), this is a real cost/ops trade-off against Pagefind.

leads:
- Prototype the maintainer's suggested aggregate-index workaround (single `pagefind --site <merged-html-root>`) as a build step run centrally after each sub-repo publishes its static output, vs. runtime `mergeIndex` per sub-bundle — decide based on number of sub-sites (few → mergeIndex fine; many → aggregate index).
- Check whether Pagefind's `mergeFilter` can tag results by sub-site (`/docs` vs `/catalog`) for a unified results UI without per-site labeling in each sub-repo's build.

## 2. Bunny.net hosting of a multi-repo path-mounted site

- Architecture: one Storage Zone + one Pull Zone in front of it is the standard static-site pattern; each sub-repo's CI uploads its build output into a subdirectory of the same Storage Zone (`/docs`, `/catalog`, `/integrations/<x>`) — this is a documented, supported pattern, not a workaround. [European Alternatives guide](https://european-alternatives.eu/blog/how-to-host-a-static-site-on-bunny-net-cdn-with-automatic-deployment)
- Existing GitHub Actions: `ayeressian/bunnycdn-storage-deploy` (GitHub Marketplace) and `R-J-dev/bunny-deploy` both take a source dir + a `destination`/target-directory param for nested-path uploads, skip unchanged files, and optionally prune stale files scoped to that destination directory only — i.e., each repo's action run is scoped to its own subdirectory and won't clobber siblings. `voorhoede/bunny-edge-deploy` additionally handles Bunny Edge Scripting for any server-rendered piece (e.g. the custom Vue SPA if it needs an edge function). [GitHub Marketplace: Bunny.net Storage Deployer](https://github.com/marketplace/actions/bunny-net-storage-deployer), [R-J-dev/bunny-deploy](https://github.com/R-J-dev/bunny-deploy)
- Atomicity/consistency: **against** — Bunny does not offer atomic directory swap or a "release" abstraction; each Action uploads file-by-file. Bunny's Geo-Replicated Storage propagates an uploaded file to other regions "within a couple of seconds" but there is **no API to confirm replication is complete** — i.e., a brief eventual-consistency window exists across edge regions after deploy, and a deploy touching many files is not atomic (a user could hit a half-updated subdirectory mid-deploy). [Bunny geo-replication blog](https://bunny.net/blog/we-have-launched-our-geo-replicated-storage/), [Bunny Storage docs](https://bunny.net/storage/)
- Versioned directories: no built-in blue/green primitive; teams doing this bring their own convention (upload to a new versioned path, then swap via an Edge Rule pointing to it) — not documented as a first-class Bunny feature.
- Rewrites/SPA fallback: Edge Rules support the classic SPA fallback trick — trigger "File Extension: Match Any" with empty extension, set Origin URL to that prefix's `index.html`; this is documented Bunny guidance, and it composes fine per-prefix (e.g., only `/apps/<x>/*` falls back to `/apps/<x>/index.html`, leaving `/docs/*` alone). [Bunny Edge Rules docs](https://bunny.net/docs/cdn/edge-rules), [Medium CI/CD w/ Bunny SPA](https://medium.com/@adihanif/how-to-implement-ci-cd-for-your-frontend-applications-reactjs-using-bunnycdn-edge-storage-42d2d46c06fc)
- `/docs` → `/docs/index.html`-style directory-index rewrites and legacy-subdomain redirects are both handled the same way, via Edge Rule triggers matching a path prefix and returning a redirect/rewrite — a documented, common pattern (blog→new-path redirect example in Bunny's own support docs), including care that trigger paths always need a trailing slash to match root. [Bunny support: Edge Rule trigger path](https://support.bunny.net/hc/en-us/articles/360001592551-How-to-correctly-set-up-the-Edge-Rule-trigger-path)
- Cache purge: supports full-zone purge or CDN-Tag-based purge of a subset of files — usable to purge only the changed prefix's tag after a sub-repo's deploy, avoiding a full-site purge on every push. [Bunny Purge Cache docs](https://bunny.net/docs/cdn/purge-cache)

negative: found no case study of anyone actually running this exact "N repos → one Bunny Storage Zone path-mounted" setup in the wild; all evidence above is from Bunny's own docs/support articles and generic deploy-action READMEs, not a real multi-repo OSS project doing it. No evidence of an atomic-deploy or versioned-release feature — this is a gap the project would have to script around itself (e.g., stage to a versioned subdir, then flip an Edge Rule) or accept the eventual-consistency window.

leads:
- Confirm CDN-Tag purge granularity (per-file vs per-directory tag) directly against current Bunny API docs before relying on it for per-repo-deploy purges.
- Test actual replication-lag window empirically (Bunny states "a couple of seconds" but offers no completion signal) before promising deploy-to-live latency to contributors.

## 3. Shared theme across different generators — real projects

- negative: could not find a documented case of a major OSS project (Rust, Astral, Deno, Tauri, Kubernetes, PSF, Mozilla) actually sharing one header/nav/design-token set across *heterogeneous static-site-generator* sub-sites the way this project intends. Rust's own community has *discussed* wanting more consistent theming/navigation across rust-lang.org properties (internals.rust-lang.org thread proposes a shared theme/dropdown for cross-linking docs) but this is an open ask, not a shipped design. [internals.rust-lang.org thread](https://internals.rust-lang.org/t/official-rust-websites/23788)
- Deno's docs (docs.deno.com) are a single Lume-based static site, not a federation of generators — so no cross-generator theme-sharing precedent there either. [denoland/docs](https://github.com/denoland/docs)
- Closest real patterns found (from adjacent domains, not docs-federation specifically):
  - **Web-component header served from CDN**: design systems like IBM Carbon and Nord ship their header/nav as custom elements loadable via a `<script>` tag from a CDN with no build step required — any generator's output can embed it as inert HTML + one script tag, sidestepping the need for framework-specific integration. This is the most directly transferable pattern for "VitePress + Astro + mdBook + MkDocs + custom SPA all embed the same header." [Carbon Design System](https://carbondesignsystem.com/developing/frameworks/web-components/), [Nord Design System](https://nordhealth.design/web-components/)
  - **Design tokens via npm package**: Style Dictionary (v4+ has first-class DTCG-format support) is the standard way to define tokens once (DTCG JSON) and compile to CSS variables, published as a versioned npm package that each generator's build consumes as a stylesheet import — decouples the design source of truth from any one generator's theming system. [styledictionary.com DTCG](https://styledictionary.com/info/dtcg/), [DTCG spec](https://www.w3.org/community/design-tokens/)
- Against pure CSS-variable-only sharing: CSS variables alone don't give you shared *interactive* header markup/behavior (menus, mobile nav) across generators with different templating — that's why the web-component approach is called out separately from token distribution; most real systems combine both (tokens for color/spacing, a web component or CDN-hosted partial for structural chrome).
- git-submodule / raw HTML partial injection is the low-tech alternative seen in smaller projects (a shared `header.html` partial injected at build time) but doesn't scale cleanly across generators with different partial/include mechanisms (Astro components vs Jinja/MkDocs templates vs mdBook's more limited templating).

negative: no evidence found of Kubernetes.io or Mozilla using a documented multi-generator shared-header system; Kubernetes sig-docs and Mozilla docs each appear to run a single generator (Hugo for kubernetes.io) rather than a federation, so they're not actually precedent for this exact problem.

leads:
- Look specifically at how ReadTheDocs' "addons"/flyout or Sphinx cross-project theme injection works — RTD explicitly federates many independently-built Sphinx (and increasingly non-Sphinx) doc builds under shared chrome; not yet investigated here.
- Investigate whether MkDocs Material, VitePress, Astro Starlight, and mdBook all support a "raw HTML head/body injection" hook (most do) as the minimal integration point for a CDN-hosted web-component header, rather than requiring native theme plugins per generator.

## 4. Shared nav via build-time nav.json vs runtime web component

- Build-time `nav.json`: generate once (e.g., a Jekyll/`jsonify`-style step, or any script) and have each generator's build fetch/embed it at build time into static HTML. Pro: zero runtime JS/network cost, nav is baked into the page, works with JS disabled, no FOUC/layout shift. Con (noted generically for build-time composition in micro-frontend literature): couples deploys — every sub-repo must rebuild to pick up a nav change, so a single new top-level link requires N repos to redeploy (or a shared rebuild trigger), which cuts against "many repos build independently." [DEV: micro-frontends build-time composition](https://dev.to/okmttdhr/micro-frontends-patterns-14-build-time-composition-3kol)
- Runtime web component / JS-fetched config: a shared script/custom-element fetches `nav.json` (or is initialized with it) at page-load time from a central CDN path, decoupling nav updates from sub-repo rebuilds — change nav.json once, every site picks it up on next load, no redeploys needed anywhere. Con: adds a runtime network fetch (mitigate with aggressive CDN caching / short-TTL + purge-on-change), brief risk of stale nav if caching is misconfigured, and requires JS for the nav to render (accessibility/no-JS fallback needed).
- Real-world convergence: multiple sources describe a "dual-phase" pattern — render a build-time-baked nav for first paint/no-JS/SEO, then hydrate/enhance with a runtime-fetched version for live updates. This gets both instant correct nav on cold cache and centrally-updatable content without redeploying every sub-repo. [Search synthesis, no single canonical source found]

negative: did not find a citable, named real-world OSS project doing exactly this dual-phase nav.json pattern for a docs federation — the pattern is assembled from generic micro-frontend and SharePoint portal-navigation literature, not a docs-specific case study.

leads:
- If choosing runtime, decide the staleness budget (cache TTL) up front — this determines whether "shared nav" edits require an explicit CDN purge step (Bunny purge-by-tag, see §2) as part of the nav-repo's own deploy.
- If choosing build-time, evaluate whether a lightweight "rebuild-all-on-nav-change" GitHub Actions dispatch across the sub-repos is acceptable, given the project already needs multi-repo CI orchestration for the Bunny deploy itself.
